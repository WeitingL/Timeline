## 1. AI 工作流程的設定

工具是終端機裡的 **Claude Code（Opus 5）**，直接對著 Android Studio 專案操作，另外用 Gradle
和一台 Pixel 9 Pro XL 做驗證。單一工具、單一長對話，沒有在多個聊天視窗之間複製貼上。

我的做法骨架很簡單，是一個循環：

```
plan  →  review  →  coding  →  review  →  (下一輪 plan)
```

**關鍵在於兩個 review 不是同一回事，也不用同一種手段。**

- **plan 之後的 review** 是我讀一份規格、再看它畫成圖的樣子，然後決定要不要讓它開工。
- **coding 之後的 review** 不是我讀 diff —— 我幾乎不逐行讀它寫的程式碼。那一段是交給**四種
  互相獨立的機制**去做的，每一種能抓到別的三種看不到的東西（第 3 節詳述）。

這個循環落實成五道關卡，寫在 `.claude/CLAUDE.md`（每次 session 啟動都會自動載入它的 context）：

```
1. 範圍    我確認要做什麼                      ┐ plan
2. 規格    ai-cowork/NNN-<slug>.md             ┘
3. 討論    docs/ 下的視覺化文件，逐張走過        → review（計畫）
4. 實作    寫程式、build、跑測試                → coding
5. COMMIT  等我在實機上跑過才可以               → review（成果）
```

**這套流程不是一開始就有的，是吃過虧之後才建立的。** 前幾輪我給一句模糊的指示，agent 就直接
實作、然後在同一個回合 commit —— 設計決策在我還沒讀過的程式碼裡就被做完了，而我沒辦法事後
審查一個我沒參與過的決定。所以我要求它把規則寫下來，然後嚴格照著走。文件裡寫得很白：
**「沒有反對」不算同意，沉默不算同意。**

五道關卡裡最重要的是第 5 道。「程式寫完」不是 commit 的觸發條件，「build 綠了」也不是 ——
**我的話才是**。這一條要寫重，是因為這個專案有好幾件事（指標事件的分派順序、手勢仲裁、捲動
方向）本來就只有實機能確認，所以「編譯過、測試全綠」在這裡是個比它聽起來更弱的宣稱。

同一份文件裡還固定了幾件我不想每次重新交代的事：語言分工（終端機中文、檔案英文、UI 字串中文）；
**查證而不要憑記憶**（引用行號或 API 之前先讀檔案，無法在沒有實機下確認的事要明說）；
**更正記錄**（診斷錯了要說哪裡錯，不能讓被推翻的說法留在文件裡）；以及七條已定案的架構承諾，
要改它們是「回到第 1 道關卡」的對話。

## 2. 開發過程：不是一次規劃完的

這點跟「先寫一份完整規劃再實作」的印象相反。

**我沒有先畫出完整藍圖。** 每一輪只處理一塊，把它跑起來、在實機上看問題出在哪，再決定下一塊
要做什麼。規格是**沿路長出來的**，不是從作業題目一次推導出來的。

| 輪次 | 做了什麼 | 下一步是怎麼決定的 |
|---|---|---|
| 1 | 分析作業要求 vs. 空白的 Compose 樣板 | 先補基礎，不急著做手勢 |
| 2 | Scaffold：座標層、時間軸 header、靜態 bar | 跑起來之後才看得出手勢需要什麼 |
| 3 | **spec 001** 手勢層：拖曳、resize、吸附 | 實機跑完才知道下一個痛點在哪 |
| 4 | 一份效能 spec —— **寫完就撤回** | 實機證明真正的問題不在效能 |
| 5 | **spec 002** 編輯鎖定、依刻度吸附、紅線置中 | 實機又抓到兩個 bug，各自再一輪 |
| 6 | **spec 003** 三個稽核找出的缺陷 | 稽核文件時掉出來的，不是用 app 用出來的 |
| 7 | **spec 004** 剩餘的算繪優化 —— **寫了但不實作** | 沒有基準量測，不值得做 |

**最能說明這個過程的是第 4 輪。** 我原本以為下一步是優化渲染，agent 也寫出了完整的 spec：
它稽核每一 frame 重複的工作、**推算**出大約是每 frame 100–150 個短命配置、列出七項改動。但它
自己的分析同時顯示，七項裡只有三項是確定的勝利，而那個量級「是純浪費，但不是 app 現在很慢的
證據」。

同一時間我在實機上發現真正難用的是**編輯與平移互相干擾** —— 點在 bar 上拖曳會把整個畫面拖走。
那是體驗問題，不是效能問題。所以那份 spec **連一行程式碼都沒寫就被我撤掉了**。

**那次撤回後來是有代價的，而我認為這是整份心得裡最值得學的一課。** 那份 spec 的七項發現裡，
有兩項其實不是「優化」而是**缺陷** —— 紅線的時鐘寫在 draw lambda 裡（app 閒置時紅線會停在
上次捲動的時間），以及示範資料放在預設參數每次重組都配置一份。它自己的 commit 訊息甚至把第一
項明確歸類為「a correctness bug, not a cost」。**撤掉整份 spec = 讓這兩個 bug 出貨。**它們活
在產品裡好幾輪，直到第 6 輪才被抓出來並修掉（spec 003）。

教訓不是「不該撤回」—— 撤回是對的。教訓是**撤回的時候應該先把裡面的缺陷挑出來**，而我當時
沒有把「優化」和「缺陷」分開看。

**同一輪之內也有多次來回。** spec 002 實作完之後：裝上去拖 bar → 整個畫面平移 → 回報 → 修；
再裝、持續拖曳 → bar 只動 15 分鐘就停 → 回報 → 修；再裝 → 可以了，才 commit。每一次都是一輪
完整的「診斷 → 解釋 → 修 → 重跑測試 → 等我驗證」。

### 我在哪裡推翻了 AI

**我否決了它對手勢仲裁的第一個答案。** 它提議用滑動**速度**區分「平移」與「切換區間」——
快速輕掃換頁、慢拖平移。我說意圖應該來自我**點在哪裡**，不是我滑多快。它接著提出用列內的空白
區域來切換區間。我說那感覺怪怪的，但說不出為什麼。它把原因想清楚並告訴我：空白區域和 bar 在
像素上相鄰、中間沒有視覺邊界，所以幾個 dp 之差就決定了「挪 15 分鐘」和「跳一天」，而誤觸的代價
不對稱 —— 一邊只是迷路，一邊改了資料。最後落在兩指切換區間：手指數本身就是意圖宣告。

**我的直覺抓到了壞設計，它的分析解釋了為什麼，兩邊單獨都做不到。**

**我一再砍範圍。** 持久選取、垂直重排序、持久化層、整份效能 spec —— 全是它提議的，砍掉的是我。

**我堅持要一段 touch slop 緩衝。** 它想讓 bar 對第一個像素就反應，論點是「吸附本來就會量化
結果」。不算錯，但年刻度下一格是**一週**，我不想要手抖一下就把任務移動一週。

**編輯樣式是我要求的。** 它出貨了一個看不見的編輯狀態。它選了斜線而不是變色，理由我接受 ——
bar 的顏色是它在圖表裡的身分。

**我改掉了它訂的一條規則。** 它寫「spec 編號只增不重用」。效能 spec 撤回後留下一個 002 的缺口，
我要求把 003 改成 002 —— 因為**缺號看起來像檔案遺失，比重新編號更糟**。
（註：2026-10-10 的 commit 訊息裡提到的「Spec 003」就是現在的 `002-edit-lock-and-scale-snap.md`。）

**我否決了一個測試護欄。** spec 003 的那個重組回歸，要真正守住需要 instrumented test 加重組
計數。我說不用，因為那也不好驗。代價寫在 spec 裡而非默默略過：**這一類回歸對 CI 永遠隱形。**

## 3. 怎麼規劃，怎麼 review

### plan：spec 模板

每一份 spec 都有同樣五節，順序固定：

| 區段 | 用途 |
|---|---|
| **Description** | 這件事做什麼，以及**明確不做**什麼 |
| **Acceptance Criteria** | 可勾選、依關注點分組 |
| **Current Logic** | 它要接上的那段程式碼的事實，附 `file.kt:line`，**必須對照工作區查證過** |
| **Expected Code Change** | 預期的改動，連同**理由**，不只是形狀 |
| **Questions** | 該由我決定的開放問題，每一題附它的建議與取捨 |

（spec 002 把第五節叫 Decisions 而不是 Questions，因為那些問題在實作前就全部答完了。）

**Current Logic 是最划算的一節。** 它強迫 agent 在提出方案之前先去讀程式碼、標出行號。好幾個
「這件事其實已經處理了」和「這裡其實已經壞了」的發現都是從這一節掉出來的。

**Questions 強迫它攤開決策**而不是默默選一個。我還明確告訴它：**一份 spec 可以反駁它自己。**
效能 spec 的撤回就是這條規則發揮作用的結果。

工作完成後 spec 末尾要補 **Resolution**，記錄每題怎麼決定、刻意沒做什麼、以及**什麼仍未驗證**。

### review（計畫）：視覺化文件

每一塊工作都有一份自給自足的 HTML 圖解頁，與 spec 編號對應：

```
docs/architecture.html    Scaffold（先於 spec 流程，無編號）
docs/gesture-layer.html   001
docs/edit-lock.html       002
docs/audit-defects.html   003
```

規格是：**單一檔案、零外部請求**（不連 CDN、不連 web font），所以離線能開、傳一個附件就能看；
**圖要承載解釋、文字只做圖說**；深淺色都用 token 定義；320dp 寬要能讀。

**這件事一開始是為了文件，後來變成設計工具。** 把「哪個 render 階段讀取捲動位置」或「相鄰兩個
像素做了完全不同的事」畫出來，會逼出文字能藏起來的含糊。

最具體的例子：前面那個「用列內空白區域切換區間」的設計，是在**畫圖階段**被殺掉的。寫成段落時
我只覺得「怪怪的」；一旦畫成「bar 與空白處緊貼、中間沒有邊界、兩側結果差兩個數量級」，問題就
一目了然。另一個收穫是圖逼出了量級感：`horizontalScroll` 為什麼不能用，寫成文字是「子元件會很
寬」，畫成圖並算出「日刻度下跨四個月約 553,000px，而視窗只有幾百 px」之後，那個決定就不需要
再討論了。

### review（成果）：四種互相獨立的機制

**我幾乎不逐行讀它寫的程式碼。** 這一段是我覺得最值得分享的部分 —— 不是因為偷懶，而是因為
逐行讀 diff 抓不到這個任務裡最貴的那些 bug（它們編譯得過、測試全綠、讀起來很合理）。我用的是
四種手段，每一種能看到別的三種看不到的東西：

| 手段 | 它能抓到什麼 | 它看不到什麼 |
|---|---|---|
| **JVM 單元測試** | 純函式、狀態機、吸附與夾限的數學 | Compose 的生命週期與階段語意 |
| **實機測試** | 手勢仲裁、手感、看得見的行為 | 需要閒置好幾分鐘才顯現的事；效能 |
| **worktree 編譯檢查** | history 上任何一個 commit 是否可編譯 | 執行期的一切 |
| **稽核文件** | **程式碼與它自己的文件之間的分歧** | 文件沒宣稱過的事 |

前三種是逐步加上去的。第四種是這個專案最後才長出來、而且**最意外**的一種。

**稽核文件怎麼變成一種 code review：** 我派了兩個唯讀的 subagent，一個拿文件去對照**原始碼**、
一個對照 **git history**。它們被交代的任務是「這些文件還正確嗎」，**不是「去找 bug」**。結果：

- 程式碼稽核發現「一條被寫下來的架構承諾被原始碼否證」—— 它在找過期的宣稱，結果找到一個過期
  宣稱，而它過期的原因是一個活著的回歸。
- history 稽核發現 writeup 的「妥協」清單漏了兩項 —— 它在檢查 writeup 誠不誠實，結果發現那個
  遺漏正好蓋著兩個已出貨的 bug。

**兩次都是從文件掉出程式碼的缺陷，方向跟預期相反。** 它之所以有效，是因為文件裡的宣稱是
**具體、可被否證**的 —— 有行號、有常數、有「每 frame 配置幾個物件」。一份寫得含糊的文件沒有
東西可以被推翻，稽核它也不會掉出任何東西。

**我也沒有照單全收。** 兩份報告共 48 項發現，其中一項是錯的（它說「18 個 Kotlin 檔」對不上任何
計數，但 `app/src/main` 當時正好 18 個 —— 它漏數了 theme 的三個檔）。每一項我都重新驗證過才
採用。

## 4. AI 出錯的案例

按**是哪一種 review 抓到的**分組，因為那比按嚴重度分組更能說明第 3 節的那張表。

### 實機測試抓到的

**4.1 它把一個指標分派行為斷言了兩次，而且是錯的。** Agent 在**兩份 spec** 裡都宣稱：Compose
的子層優先分派會讓任務 bar 在水平手勢上贏過祖先的 `Modifier.scrollable`，所以拖曳 bar 絕不會
平移時間軸。它兩次都標註了「沒有實機就無法驗證」—— 我現在認為那正是警訊：**替一個假設貼上
標籤，不等於沒有依賴它**。它在上面蓋了兩個功能。

我裝上去、拖了一下 bar，整個畫面跟著平移。真正的原因跟分派順序無關：bar 和祖先的 scrollable
用同一個 touch slop、累積同一個 x 位移，所以在**同一個指標事件**上跨越門檻 —— 而它的迴圈把那
一個跨越事件留著沒消耗就去等下一個了。一個未消耗的事件就足以把整段手勢交出去。

修法兩層：在跨越的事件就消耗（治根因），加上編輯中直接停用祖先捲動器（把競爭移除而不是去贏它）。

**4.2 拖曳只動一格就停住。** 實機上持續拖曳，bar 只移動 15 分鐘。`positionChange()` 在事件被
消耗之後回報 `Offset.Zero`，而它的迴圈是先消耗再讀取。

這次的處理我很滿意：我指出症狀後，它說自己「記得這個 API 行為但不確定」，於是在改任何東西
**之前**先寫測試把契約確立下來（正是「查證而不要憑記憶」那條規則）。結果發現
`PointerInputChange` 是純 Kotlin class、沒有 Android 依賴，可以在 JVM 測試裡直接建構。

### 我回報症狀、但它第一次診斷錯方向

**4.3** 我回報「編輯同一條 bar 第二次時，它會倒退回原始時間」。它的第一個答案是 Activity 重建
—— 旋轉、`remember` 撐不過去。講得自信又詳細，而且**跟我描述的完全不符**：我根本沒旋轉螢幕。

我用更精確的症狀把它推回去，它才找到真正的原因：`pointerInput` 的 key 是
`(task.id, pxPerMinute, barWidthPx, handlePx)`，而 `Task` 被 lambda 捕捉了卻**不在 key 裡**。
移動不改 duration → bar 寬度不變 → 沒有 key 改變 → suspend block 從不重啟 → 一直持有第一次
組合時的那個 `Task`。

它接著講了一個我記下來的觀點：與其把 `task` 加進 key，不如把 `beginDrag` 改成接收 `taskId`
並從即時清單解析 —— 讓這個 bug **無法被表達**。更值得注意的是，原本測試裡有一項叫
「a second drag starts from the committed position」而且是綠的 —— 它之所以綠，只因為那個測試
每次都重新從清單讀取。Bug 活在 Compose 的 key 語意裡，那個測試從它的角度看不到。

### 單元測試抓到的

**4.4 一個斷言錯誤的測試。** 它寫的測試斷言邊緣自動捲動會讓視窗和 bar 移動相同的量。失敗了：
10 分鐘對 15 分鐘。**實作是對的** —— 開啟即時吸附時 bar 以整格跳動，不可能連續追蹤。是測試
寫錯。後來拆成三個測試，分別釘住：關閉吸附時完全相等、開啟吸附時漂移小於一格、撞到夾限時一起
停住。

這算它贏不算輸 —— 失敗的測試抓到了錯誤的斷言，那正是測試的用途。但它提醒我：**生成的測試可能
把生成的誤解也一起編碼進去。**

### worktree 編譯檢查抓到的

**4.5 一次切成七個 commit，大部分編譯不過。** 它把一次改動依關注點切開。worktree 檢查（它自己
訂的規則要求的）顯示多數 build 不起來：那批 API 改動在整個 package 裡形成相互依賴叢，沒有任何
檔案層級的切法能讓每一步都編譯。它 reset 之後重整成一個編譯得過的 commit。

> 精確一點：那七個裡有一個是 docs commit，所以是**六個程式碼 commit 收成一個**（連 docs 共兩個
> 落在 main）。而那七個被 reset 掉了，只存在於我本機的 reflog —— **push 或 bundle 都不會帶走
> 它們**，所以 reviewer 翻不到，`32cfca4` 的訊息也只解釋了「為什麼是一個 commit」，沒有記錄這段
> 經過。這段敘述是過程的記錄，不是能從 repo 驗證的證據。

### 它自己 review 時抓到的

**4.6 一個會自己取消的手勢。** 它在修 4.2 時自己檢查出來。`pointerInput` 的 key 包含
`barWidthPx`，而它在 resize 的**第一個 frame** 就會改變 —— suspend block 重啟，把正在設定它
的手勢殺掉。平移的 bug 一直蓋著它。根因和 4.3 相同：**會在手勢進行中變動的值，不該放進 key。**

### 結構驗證腳本抓到的

**4.7** 一個混進 hex 色碼的全形數字（`#79839５`），會無聲地讓一個深色模式 token 失效；以及文件
裡用到卻從未定義的 CSS class，會讓兩個區段渲染成沒有樣式。兩者都在拿給我看之前被它自己跑的
驗證腳本抓到 —— 而那些腳本其中一支第一版本身也是錯的，誤報了另一個檔案有問題，後來它自己更正。
（全形數字那一項在 commit 之前就修掉了，所以 git 裡沒有痕跡；CSS 那一項記在 `2d0e1b8` 的訊息裡。）

### 稽核文件抓到的

這三個是最後一輪的收穫，也是四種 review 手段裡唯一能抓到它們的那一種。

**4.8 一行引數讓每條 lane 每 frame 重組。** `rememberUpdatedState(...)` 的引數位置寫了
`laneOriginX = axis.xOf(start, state.viewportStartMinutes)` —— 引數在 **composition 階段**求值，
所以每個捲動 frame 都讓每條 lane 失效。它牴觸 `.claude/CLAUDE.md` 的架構承諾，而兩份 writeup
都把那條承諾當成「這個專案做對的事」來列。

最難看的是它自己的註解寫著「必須每 frame 重新讀取，而不是在 composition 捕捉」—— 它**就是**在
composition 捕捉的，而它之所以還能保持新鮮，純粹是因為那個不該發生的重組。註解自我否證。

諷刺之處：那個 holder 本來是為了修 4.6 而引入的 —— **修一個 Compose 生命週期問題的同時製造了
另一個**。

**4.9 / 4.10 兩個因為撤回 spec 而出貨的 bug。** 紅線的時鐘寫在 draw lambda、示範資料在預設參數
（詳見第 2 節）。這兩項是 history 稽核在檢查 writeup 的「妥協」清單時發現遺漏的。

三項都已在 spec 003 修掉。但**最關鍵的驗收標準仍未驗證** —— 「lane 不再於捲動時重組」需要
Layout Inspector。改動在建構上是對的，但「在建構上是對的」正是 4.1 所相信的事。

### 它在哪裡最吃力，以及我認為的原因

**手勢與指標事件處理，差距很大。** 4.1、4.2、4.3、4.6、4.8 全是同一個家族。

我的解讀是：這個任務裡其他每一塊都有**可以便宜驗證的表面**。Layout 和繪圖要嘛看起來對、要嘛
不對。座標運算是純函式加單元測試。但指標仲裁與 Compose 的階段語意是一組**執行期契約**，發生在
彼此是兄弟或祖孫的 modifier 之間：誰消耗、在哪一個 pass、用多大的 slop、`pointerInput` block
活多久、哪一個表達式落在哪一個階段。這些都不會出現在型別裡，也不會出現在單元測試裡。它可以寫出
編譯得過、56 項測試全綠、讀起來很合理、但就是錯的程式碼 —— 而且它沒有任何回饋訊號會告訴它。

這也解釋了為什麼它的信心校準**偏偏在這裡**失準：對於它能檢查的事情，它的保留是恰當的；對於
它唯一檢查不了的領域，它悄悄地過度自信。

**而這正是我為什麼需要四種 review 手段，而不是一種。**

第二個吃力的地方是**知道什麼時候該停**（見第 2 節的效能 spec）。

## 5. 對最終成品的評價

產出：32 個 commit、19 個 Kotlin 檔（`app/src/main` 全部）、56 項 JVM 單元測試（其中 1 項是
Android Studio 樣板附的）、19 個 Compose preview、4 份視覺化文件、4 份 spec（1 份 parked、
另有 1 份早先撤回）。開發集中在 2026-10-10，單日約六小時，加上 10-11 的稽核與修正。

### 我認為好的部分

- **`TimeAxis` 是純的，完全不 import Compose。** 時間↔像素轉換、吸附、刻度產生都是一般函式，
  能在 JVM 上測，不需要裝置也不需要 Compose test rule。其他所有東西都掛在它上面。
- **捲動位置存在時間域**，而不是像素偏移。切換刻度或縮放時視窗左緣自動釘在同一個時刻。
- **時間軸不用 `Modifier.horizontalScroll`。** 它需要一個跟整段時間範圍一樣寬的子元件 ——
  日刻度下跨四個月約 553,000px。共用的 `scrollable` 讓內容永遠只有一個視窗寬。
  （控制列那排吸附 chip 有用 `horizontalScroll`，那是另一回事。）
- **吸附錨定在 origin，而 origin 是本週一** —— 15 分鐘、1 天、1 週三種網格都整除同一個格線系統。
- **編輯粒度跟著視覺粒度走** —— 日 15 分、週/月 1 天、年 1 週。
- **文件做得夠具體，以至於它可以被稽核。** 這在一開始不是目標，但它最後抓到了三個 bug。

### 哪些是妥協

- **「捲動不造成重組」這條承諾被破壞過一次，而修復尚未實測。** 它是我最想拿出來講的設計性質，
  結果它被一個引數表達式無聲地破壞了好幾輪。已修，但需要 Layout Inspector 才算真的驗證。
- **這一類回歸沒有 CI 護欄。** 我主動放棄了測試護欄（代價寫在 spec 003 裡）：它對 CI 永遠隱形，
  只能靠 review 或稽核。它已經發生一次了。
- **編輯結果撐不過 Activity 重建。** 旋轉螢幕就回到示範資料。`rememberSaveable` 加自訂
  `Saver` 可以解決，我把它排除在範圍外。它**刻意不在上面那張清單裡**：在一份跑示範資料的作業
  裡，捲動效能與互動手感是每一次操作都會碰到的，而旋轉是偶發的。如果這是一個有真實資料的產品，
  優先順序會反過來，它會排第一。
- **列用 `Column` 而不是 `LazyColumn`**，且每條 bar 不論是否在水平可視範圍內都會被組合。
  六筆任務沒問題，六百筆不行。
- **刻度清單每 frame 重建、而且重建兩次**（header 與網格各一）。推算量很小，在有真實基準之前
  刻意不動 —— 這是 spec 004 parked 的內容。
- **編輯鎖定用了兩套機制，而一套應該就夠。** 保險起見，因為只用一套的版本正是實機上失敗的那個。
- **spec 002 最後是一個 commit**，而不是它應得的六個。

### 有更多時間我會做什麼

1. **優化畫面滾動的效能，並把剩下幾個 bug 收掉。** 這一項包含三件已經被記錄但還沒做的事：開
   Layout Inspector 把 spec 003 那條「lane 不再於捲動時重組」的未驗證標籤劃掉（同一個 session
   也會順便拿到 spec 004 要的基準）；spec 004 裡 parked 的四項算繪優化 —— 刻度清單每 frame 在兩
   個 canvas 重建、標籤重複量測、熱路徑上的 `Duration` 配置；以及驗證邊緣自動捲動時，bar 被裁切
   到視窗外的情況下 `fingerX` 是否仍然正確（算式在建構上是對的，但那條路徑從未被走到）。

2. **把動畫加進來。** 目前只有兩處有動畫：導覽（`◀ 今天 ▶` 與兩指滑動）會平滑移動視窗，以及
   bar 兩端 grip 的探索提示。其他全是瞬間跳變 —— 吸附時 bar 直接跳到格線上、切換刻度時整個畫面
   瞬間換掉、縮放是一步到位。這些都是使用者每一次操作都會碰到的地方，而現在它們都沒有過渡。
   吸附那一項我認為最值得做：讓 bar 用一小段彈性動畫落到格線上，比直接跳過去更能讓人理解「它
   被吸附了」而不是「它亂跑」。

3. **讓使用者用垂直拖曳決定任務順序。** 這一項是刻意砍掉的，不是漏掉的 —— spec 001 的第 4 題和
   spec 002 都明確把它排除，理由是「列目前不代表任何語意，重排序編碼不了資訊」。但那個理由有
   期限：一旦列開始代表某個人、某個資源，或單純是使用者自己的優先順序，順序本身就變成資料。
   手勢的位置也已經空著 —— 目前在 bar 上垂直拖曳是穿透給列表捲動器的，那正是重排序該接手的軸向。
